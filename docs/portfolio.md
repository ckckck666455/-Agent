# 小美 · 全品类生活馆 Agent

> 一个可运行的电商 AI 智能体：客服 / 售后 / 导购 / 选品分析 / 营销分析。  
> Python + FastAPI + DeepSeek Tool Calls + RAG + SQLite + Docker + 评测。

## 1. 一句话

把“会聊天”做成“能查真实数据、能按人群推荐、能处理售后、能被评测、能降级”的业务 Agent。

## 2. 解决什么问题

电商客服场景里，通用聊天模型有三个硬伤：

1. **编事实**：编库存、编物流、编优惠。
2. **越权**：查别人订单、乱发券。
3. **情绪崩**：顾客一急，模型开始辩解、阴阳怪气，订单彻底丢。

项目用“工具 + 规则 + 评测”把这三件事压住。

## 3. 方案

```text
用户
 → 限流 / 输入清洗
 → 情绪分流（愤怒 → 工单转人工）
 → 意图识别 + 实体/画像
 → RAG 检索（FAQ/政策）
 → Agent 工具循环（20 个工具）
 → 输出护栏（事实、语气、长度）
 → SQLite 持久化 + 审计
 → 回复 / 工单
```

### 关键设计

- **工具不暴露 user_id**：身份由服务端注入；订单校验归属。
- **业务规则代码化**：券上限 20、同一用户一张、退货窗口/拆封规则、物流单号幻觉拦截。
- **分人群**：老人/儿童/男士/女士/家庭，不同问法和安全边界。
- **服务补救**：顾客质疑态度时先道歉、复述、给选项；拦截“不演了/你爱买不买”等话术。
- **RAG**：TF-IDF 字符向量基线，25 条检索评测；可替换 dense embedding + rerank。
- **双模式**：DeepSeek 在线 + 离线规则引擎；模型失败自动降级。
- **ERP 适配**：mock ERP/OMS HTTP 客户端，超时/重试/幂等/鉴权。

## 6. 取舍

- **自研循环 vs LangGraph**：先用自研循环把业务跑通；LangGraph 是下一步的显式图编排（见 `docs/langgraph-migration.md`）。
- **TF-IDF vs dense RAG**：25 条 FAQ 的规模，TF-IDF 足够稳；dense 是生产升级，不是 demo 必需。
- **规则 vs 模型**：情绪、券、退货、订单归属属于硬约束，规则更可测；开放表达交给模型。
- **单 Agent vs 多 Agent**：一个可解释的状态机比五个互相对话的 Agent 更适合客服。
